# Changelog

All notable changes to the Two Payment module for PrestaShop will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **The Two payment option is withheld from buyers in a country the merchant is not set up to transact with** (TWO-40), instead of being offered and then declined
  - The allowlist is server-supplied on the merchant record and read from the **same single `GET /v1/merchant` fetch** that already feeds the offerable term list, the default term, the platform minimum and the invoice-upload flag — a fifth cache on the shared TTL and clock, so this costs no extra request per checkout render
  - **A merchant record that does not carry the field is unrestricted; a record that carries it and names no country permits none.** The absent case is the only fail-open state, and it is what a shop sees while the backend serving it does not publish the field yet — so no shop's payment option narrows until Two publishes a list for it. A field that IS present, and is null, an empty list, or not a list at all, permits no buyer country: the backend has answered, and its answer is not "unrestricted". The three restricting states are told apart in the shop log so a shop offering Two to nobody is diagnosable from the log line alone
  - **Fail-open on any API fault.** The gate reads cache only and never makes a call of its own, so a shop that cannot reach Two keeps offering Two; a merchant who *does* have a restriction keeps it across a blip via the same serve-stale behaviour as its sibling caches. A restriction is dropped when the merchant identity changes, so a new API key never inherits the previous merchant's countries
  - **Enforced at every submission point, from one shared helper.** The payment-options hook withholds the tile, `controllers/front/payment.php` refuses a POST from a page rendered before the record changed, and both order-intent paths refuse too — otherwise a stale checkout page walks straight past the display gate into an opaque decline at order creation. The buyer sees the module's existing generic "not available" message
  - **Every refused order and every refused order intent is logged at warning severity**, naming the merchant, the buyer country and which of the three restricting states refused it. The display gate stays latched to one line per request, since core asks for payment options several times per render
  - **Gated on the billing country, falling back to the shipping country** when the billing address carries none — the same value the order submits as the buyer's company registration country, which is what the backend checks the list against
- **The four calls the browser makes straight to Two now identify the client, like the server-side calls always have** — `client=PS` and `client_v=<version>` as query params on company search (`GET /companies/v2/company`), company detail (`GET /companies/v2/company/{lookup_id}`), order intent (`POST /v1/order_intent`) and sole-trader autofill (`GET /autofill/v1/buyer/current`)
  - The PHP side has attached this pair to every call since it gained `getTwoClientParams()`, but the browser-side calls sent neither, so a shop's traffic arrived partly unattributed and version-adoption figures counted only the half of it that left the server
  - **Query params, not body fields, including on the POST.** That is not a decision made for the browser: `setTwoPaymentRequest()`'s POST/PUT branch already puts them on the URL rather than in the payload. The order-intent body is also a payload the server builds and Two validates, so adding to it would be a contract change rather than a metadata addition
  - **The values are read from the config the module publishes** (`window.twopayment.client` / `.client_version`), never restated in JavaScript, so a version bump stays a PHP-only change. Either param is omitted rather than sent as a literal `undefined` if the config is somehow absent
  - Only calls to Two's own host carry them. The shop's own module front-controller URLs (`TwoSoleTrader.moduleUrl()`) are a different server and are deliberately left alone
- **The billing organisation number and company name are now persisted on the order** (TWO-40), so post-order paths stop sending an empty organisation number to Two
  - Two new columns on `ps_twopayment` — the module's OWN order-keyed table. No core table is altered and no class override is involved, consistent with `createTwoTables()`'s standing rule: *"Only create our own module tables - no modifications to core PrestaShop tables"*
  - **The problem it solves.** `getTwoUpdateOrderData()` runs in admin/webhook context *after* placement, by which point core has rotated the cart, so the cart-scoped session company is gone and the resolver falls through to reading `ps_address.dni` — empty for a `TWO:`-prefixed identifier, and empty entirely on any country without `need_identification_number`. So `hookActionOrderEdited` (admin edits a line or quantity) and `hookActionAdminOrdersTrackingNumberUpdate` (admin adds a tracking number) both PUT `buyer.company.organization_number` as `''`. That was the status quo for *every* buyer on most countries, not only sole traders
  - **This is the pattern that method already uses**, not a new one: `two_day_on_invoice` is persisted and read back as `$storedTerm` for exactly this reason — *"the update path runs in admin/webhook context with no buyer term cookie… otherwise the fee would be recomputed"*. Same problem, same shape, same place
  - **Captured from the billing/invoice address specifically** — `getTwoCheckoutCompanyData(new Address($cart->id_address_invoice))`, which is a fail-soft wrapper over the very resolver that builds the payload. Not a second resolution path, and not the raw submitted field: the value stored is the one the order was actually placed with. Taken in the same request as order creation, while the cart-scoped record is still readable
  - **Writes are presence-conditional, and are staged only after the columns are confirmed writable.** Of the eleven `setTwoOrderPaymentData()` call sites, ten are status/webhook updates that know nothing about the company; an absent key means "leave the stored value alone", never "overwrite with empty". Getting that wrong would silently erase the value on the next status change
  - Reads prefer the stored value and fall back to live resolution when it is empty, so orders placed before this release behave exactly as they do today. There is deliberately no backfill — the value is only knowable from the buyer's own request
  - Keyed by order id rather than address id on purpose: PrestaShop re-keys an address on edit-after-order-use (`CustomerAddressPersister::save()` clones to a new row and soft-deletes the old), which would orphan anything keyed by the old id. An order id is stable for the life of the order
- **A Diagnostics table of arbitrarily-named custom request headers** — the merchant adds any number of name/value rows and ticks per row whether it should also be sent from the buyer's browser. Shops whose own web application firewall admits Two's traffic only when it carries an agreed header can now name that header themselves, in any number
  - One `Configuration` key holds the rows as JSON. `HelperForm` has no repeatable-row field type, so the table follows the module's own precedent for a tabular control (the per-term surcharge grid): a `type => 'html'` field whose values are read and escaped server-side, with add/remove handled by the admin JS. A hidden marker input travels with it, so removing the last row saves as an empty list rather than as "field absent, keep what is stored"
  - **Every configured row is sent on every server-side call, including the unauthenticated order-intent path** — a firewall the rows exist to clear does not care whether Two would have authenticated the request. Only rows ticked for the browser are published to the page at all
  - **A row that could not be sent as a header, or whose name is reserved, is refused at save time with a message naming the rule, not silently dropped** — a name outside the RFC 7230 token set; a reserved name, matched case-insensitively; a value containing anything outside printable ASCII (a line break splits the request, a control character poisons logs, a non-ASCII byte is encoded ambiguously between the store, curl and the firewall); or a named row left without a value
  - **The reserved names fall in four groups:** `Host`, `Content-Type`, `Content-Length`, `Accept`, `Accept-Language`, `X-API-Key`, `X-Vendor-Name`, which the module or curl sets on its own calls, so a row would override what the store actually sends Two; the RFC 7230 hop-by-hop headers `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, which govern the connection rather than the message and desynchronise the request curl frames; `Accept-Encoding` and `Expect`, which change the shape of what comes back rather than what is sent — the module sets no `CURLOPT_ENCODING`, so a merchant asking Two for a compressed response would get a body every response parse then fails to read, and `Expect` hands curl a 100-continue handshake to negotiate on a request it did not frame for one; and `Authorization`, `Cookie`, `X-Forwarded-For`, `X-Real-IP`, which carry credentials or caller identity a merchant must not be able to forge
  - The reserved-name check runs again when the stored rows are read, so a reserved row is dropped regardless of when it was stored

### Removed
- **The "Automatically fulfil orders with {brand}" master switch (`PS_TWO_FINALIZE_PURCHASE`)** (TWO-24769 follow-up), aligning PrestaShop with woocommerce-plugin/magento-plugin's simpler model. The Fulfilled-status multiselect is now the sole trigger: any of its selected statuses fires fulfilment, an empty selection means never. `upgrade-2.7.14.php` clears the Fulfilled-status mapping to empty on shops where the switch was off, so they keep fulfilling manually rather than being silently switched to auto-fulfil; shops with the switch on keep their existing mapping unchanged
- **`vat_number` is no longer accepted as an organisation-number fallback** (TWO-40, Doug's explicit ruling)
  - `Twopayment::extractOrgNumberFromAddress()` used to fall back to the address's `vat_number` when `dni` held nothing usable, returning it verbatim when its two-letter prefix did not match the address country and stripping the prefix when it did. Both branches are gone
  - **A VAT number is not an organisation number.** They are issued by different registers and coincide only in some countries, by accident rather than by rule. Relaying one as the other asks Two to run a credit decision on a number that does not identify the buyer's company — convenient when it happens to work, wrong in principle either way
  - **This narrows the fallback chain and is a real behaviour change.** An order where `vat_number` held the only org-number-shaped value on the address now sends no organisation number at all, and Two's own resolution decides what happens next — which is the intended outcome: an unresolvable org number should fail loudly rather than be papered over with a number of a different kind. Merchants in countries where the two identifiers do coincide may see orders that used to resolve silently now require the buyer to pick their company from the search
  - The write side already refused to touch `vat_number`, for the mirror-image reason (a non-empty `vat_number` on a foreign address makes core apply a B2B reverse charge, silently zeroing VAT for a buyer who is not VAT-registered). The read side now agrees with it. The remaining chain is `dni`, then the in-memory `companyid` the order-intent controller sets — **`companyid` is NOT dead code** despite there being no such column on `ps_address`, and there is now a test saying so by name
- **Dead code removed** (TWO-40): `TwoCompanySearch.getCompanyData()`, `.isValidCompanyData()`, `.reset()`, `.storeCompanyDataInSession()` (and with it the last `sessionStorage['two_company_data']` write) and `.getCompanyDataFromSession()`; `TwoCheckoutManager.getCompanyData()`; `TwopaymentOrderintentModuleFrontController::getStoredCompanyId()`; and three unreachable private helpers on the `CustomerAddressFormatter` override — `addConstraints()`, `addMaxLength()`, `getFieldLabel()` — plus the `$definition` property that existed only to feed them; and the unread `public $enable_company_name` property on `Twopayment` with its assignment (deleted rather than renamed — renaming a public property would be a BC break for third-party code reading it). `TwoOrderIntent.reset()` is a different method, is in use, and is untouched
- **The "Development" `PS_TWO_ENVIRONMENT` option** (TWO-25455). It had no entry in any of `ENVIRONMENT_HOSTS`, `PORTAL_HOSTS`, `BUYER_PORTAL_HOSTS` or `TwoSoleTrader::$signup_hosts`, so selecting it silently fell back to sandbox hosts everywhere — indistinguishable from leaving the setting unset, and it was also the install-time default, so every fresh install started on it. The admin dropdown now offers only Staging and Production; the install default is now `staging`. A guarded upgrade script (`upgrade-2.7.8.php`) rewrites any shop still stored on `development` to `staging`

### Fixed
- **The payment-terms fee rendered twice at checkout on an upgraded shop** — once as its own totals row, and again as an ordinary line item in the cart-summary product list, captioned twice within that one line
  - `actionPresentCart`, the hook that moves the fee out of the presented cart's products into a totals row beside Subtotal and Shipping, was registered by `install()` only. `install()` never runs again on an existing shop, so no shop that upgraded into that behaviour ever got the hook. It is now in the constructor's self-heal list for hooks introduced after a shop was installed, which heals each shop on its own first front-office render (core scopes both the check and the write to the context shop)
  - The caption appeared twice inside the line because core links the same product twice there — once around its image, once around its name — and the label fix-up rewrote every link it matched. Only the link carrying the product's name is captioned now; the other is unlinked and its image kept
  - **Decided per line, not per page**, since one page can hold several renderings of the same cart — the header mini-cart beside the checkout summary — with different markup. Where a theme leaves the name unlinked, or links it together with the image, core's own name node carries the caption instead, so the fee is never named twice in one line whichever shape the theme uses
- **One company-search widget could delete another's only route out of manual entry.** `removeBackToSearchLink()` and `removeSelectDifferentSoleTraderLink()` swept every matching element in the document, so a second widget rendering or clearing its own link took the first widget's with it, stranding that field in manual entry with no way back to search
  - The sweep is now scoped to the widget's own field wrapper. It still has to be wider than the widget's own reference — a link a previous instance left on the same field has no live reference at all — so it stays a query rather than a single node, and the existing orphan-collection behaviour is unchanged
- **A shop with NO copy of a shipped override was left with none forever** (TWO-25265), so its address form rendered in core's field order with the country selector near the end rather than above the company field
  - `TwoOverrideMigrator::refresh()` skipped every path that had no file at the shop level, and returned before `installOverrides()` whenever it had deleted nothing. It could repair a stale copy but never an absent one — the state left behind when a delete succeeds and the rebuild after it does not — and each later version's refresh call skipped the same shop again for the same reason
  - It now counts a missing file the module still SHIPS as work to do and re-runs `installOverrides()`, which writes it fresh and stamped at the installed version. A path named as RETIRED is still skipped when absent: for that one, absent is the finished state
  - `upgrade/upgrade-2.7.10.php` carries the repair. Shops already on 2.7.9 have run every earlier script, so the fix needs a filename none of them has seen
  - **The repair reaches a shop only during a module upgrade.** `refresh()` is called from upgrade scripts and from nowhere else — not from `install()`, not from a hook, not at runtime. Nothing repairs the tree automatically between releases: a shop that loses it again needs a merchant or admin to install, reset, or disable-and-re-enable the module, each of which re-runs core's own `installOverrides()`. What changed is that an unrepairable state became a repairable one, not that repair became continuous
  - The class index is now regenerated through whichever generator the running PrestaShop has. 8.1 moved it onto the `prestashop/autoload` package and 9 deleted `Tools::generateIndex()` outright, so the old single spelling was a fatal on 9 — swallowed by the upgrade script's `catch`, which left the shop unrepaired while reporting the upgrade as successful
  - A refresh whose `installOverrides()` reports failure is now logged at severity 2 rather than as info
- **A buyer who gave their company on the shipping step but left the billing address blank had no buyer company sent to Two at all** (TWO-25503). `buyer.company` now falls back to the shipping address whenever the invoice address identifies no company, on the order intent, the order-create and the order-update payloads alike
  - Resolved as a whole record rather than field by field: the company name and the organisation number always come from one source, because a name from one beside a number from another names a buyer that does not exist. Where that source is an address, the country prefix comes from it too, so it agrees with the register the number was issued by
  - **The persisted snapshot is one of those sources, and is honoured as a pair too** (TWO-40). A snapshot holding a name but no organisation number is no longer completed from an address — half a snapshot beside half an address is a buyer the order was never placed with. That shape is ordinary rather than corrupt: an invoice address carrying a company name and no identification number snapshots exactly that, and the order was created with it. The snapshot has no country column, so on this one path the country prefix still follows the invoice address rather than the stored pair
  - The billing address keeps its own country — only the buyer's identity moves
  - Second cause, also fixed: a company the buyer had explicitly picked was discarded whenever the record was stamped with a different address id from the one being resolved. The record is already scoped to the cart, so the cart's other address is the same buyer's own selection, not a switch away from it. A stamp naming an address outside the cart is still discarded
  - Third cause, also fixed: a company picked for a delivery address **in another country** was destroyed before the fallback could read it. Every payload resolves the invoice address first, and the country guards cleared the whole record on the mismatch. A record held against the cart's other address is now declined for the address being resolved rather than deleted, so it is still there when that address is resolved a moment later. It is also no longer borrowed as a bare company name for an address in a different country. A legacy record carrying no country marker is still cleared by either address, since there is no country it could be valid for
  - The order-intent AJAX handler resolves the same record earlier in the same request, so it identifies the address it is resolving too — otherwise it destroyed the record before the payload it feeds could read it
  - **Out of scope, and it bounds what this change reaches:** the two company gates upstream of these payloads both consult the invoice address alone and are untouched. The payment-submit controller refuses unless the invoice address yields *both* a company name and an organisation number — strictly stronger than this fallback's trigger, which needs the invoice address to have neither — so on the payment-submit path the fallback cannot yet fire. The browser-side prompt decides on the same invoice-only basis. The fallback is therefore live on the order-update payload, and on the create and intent payloads wherever invoice resolution is already non-empty through the cart-scoped company record. Widening the gates is the payment-availability question, tracked separately
- **`hookPaymentOptions()` now withholds Two outright when the merchant's offerable payment terms have never been resolved from Two's API** (TWO-25503), instead of silently offering the hardcoded `PAYMENT_TERMS_OPTIONS` preset — a cold cache, a merchant-record fetch that has only ever failed, or a merchant-identity change that just invalidated the cache all withhold now, logged once per request like the API-key and country gates next to it. That preset remains, unchanged, as a build-time UI seed for the admin checkbox screen before a merchant has any backend data — never a runtime substitute for it
- **A completed sole-trader enrolment filled the registered address but never the buyer's phone number** (TWO-25503). The response has always carried `phone_number`; it was the one field of it that landed nowhere. It now fills the `phone` input through the same address fill, marked and gated exactly like street, postcode and city
- **The version published to the browser dropped its commit-hash suffix**, so one shop reported two different versions depending on which side of the module made the call. The config the browser reads was built from the raw module version, while `getTwoClientVersion()` — what every server-side call sends — appends `+<sha7>` whenever a deployed commit is resolvable. Both sides now come from that one helper
- **A buyer who completed a real OTP verification in the sole-trader signup popup could be rejected and looped straight back into the same popup** (TWO-40, live bug reported by Doug)
  - Root cause: `getCurrentBuyer()` re-validated the popup's response against `checkoutEmail()` — the separate email PrestaShop's own personal-information step collected for the order — for EVERY caller, including `bindPopupMessageListener()`'s 'ACCEPTED' handler, which fires only after the buyer has already authenticated in the popup by whatever email they entered there. Nothing in the flow writes that email back into PrestaShop's own form, so a buyer whose registered sole-trader email genuinely differs from the order's checkout email got a successful OTP, then had this check silently disagree with the server and reopen the popup — on every subsequent attempt, since the mismatch was permanent, not transient
  - The email-match heuristic is still correct, and kept, for the OTHER caller of `getCurrentBuyer()` — the passive lookup `startEnrollment()` issues before any popup is shown, checking whether an existing Two session cookie happens to belong to the same person filling out this checkout. That is the only path where nobody has authenticated anything yet, so a heuristic is all there is to go on
  - Fix: `getCurrentBuyer(trustedIdentity)` — the popup-completion path now passes `trustedIdentity = true` and applies whatever buyer the endpoint returns without re-checking its email against the checkout form at all. The two emails identify different things (who authenticated vs. who the order is addressed to) and were never required to match
  - Adversarial review (Han + Vader) found the fix reopened the same symptom via two races rather than the guaranteed email mismatch: a 404 on the buyer lookup immediately after a real 'ACCEPTED' (ordinary read-after-write lag, not "not registered") fell straight through to reopening the popup - now retried once, after a short delay, before giving up; and a genuine 'ACCEPTED' arriving while a different lookup was already in flight silently no-op'd on the existing re-entrancy guard, dropping the authentication event entirely - the busy call's own completion now re-issues a trusted lookup once it clears
  - A further review round (Han + Vader, convergent) found the retry fix itself released the re-entrancy guard ~800ms too early - a `setTimeout` scheduled from inside a `.then()` handler doesn't delay that handler's own `.finally()`, so the guard read "free" for the whole retry wait, reopening the same concurrent-lookup window for a second 'ACCEPTED' landing mid-wait. The guard now stays held for the entire wait and is released only right before the retry fires. The same round also found the one-retry cap could be reset to zero by an intervening abandon/resume cycle - `resumeIfStillEnrolling()` now forwards the retry flag instead of defaulting it back to unset
- **Completing the sole-trader signup populated nothing at all — not the company name, not the organisation number, not one address field** (TWO-40 follow-up, live bug on staging)
  - Root cause: `applyBuyer()` received the completion response, read `company_name` and `organization_number` off it with the correct field paths, and then wrote neither to any input. It posted the identity to the `saveCompany` session action, published an in-memory selection, called status/prompt UI that resolves through the `.two-sole-trader` container and therefore silently no-ops on the address-editor page, and dispatched a `two:sole-trader-ready` event that nothing listens for. There was no write path to `company`, to the hidden `companyid`, to `dni`, or to any address field. The whole purpose of the flow is for that data to land in the checkout, so the buyer completed a signup and looked at an empty form
  - The completion now adopts the enrolled identity into the form the buyer is looking at: `company_name` into the visible company field, `organization_number` into the hidden `companyid` **and its `data-two-company-name` pairing tag together** — and, unless it is a `TWO:` identifier, into the visible identification field too — and the whole of `billing_address` — street, building, apartment, postal code, city and region — into `address1` / `address2` / `postcode` / `city` and the state field, by the routing rules below. Works on the address-editor page and the payment tile alike — only the status/prompt UI stays container-scoped, because there is nothing to show where there is no container
  - **The pairing tag is what makes the write survive.** This adoption was attempted three times before and withdrawn each time, always for the same reason: an untagged non-empty `companyid` is read by the stale-pairing check as company-set / number-set / tag-absent — "the buyer has edited past a stale selection" — and wiped on their very next keystroke in the company field. Every write now goes through the single writer that sets the field and its tag as one operation, so it presents a *valid* pairing. **The guard itself is untouched**: a buyer who genuinely retypes a different company name still clears the selection, exactly as before
  - Every write reuses the writer a real company selection already uses — same autofill-marker vocabulary, same scope resolution, same mirror-write reporting — so the plugin's own values stay recognisable as its own on the next render instead of reading as buyer-authored and pinning the address against future syncing
  - **The buyer's registered country is deliberately NOT written over the form's country.** The enrolment's token, and the session company just stored, were minted against the country resolved from the live form; the server discards the entire session company the moment the saved country disagrees with the cart's invoice-address country, so writing the registered country over it would destroy the enrolment being completed
  - **Every field the response carries now lands somewhere.** `building`/`apartment` take `address1` with the street moving to `address2`; where neither is given the street takes `address1` and the second line is left alone. **No de-duplication against the street** — it is valid for an address to carry the same text on both lines, so an address whose `building` equals its `street` writes it twice. `region` goes to the form's state/county select where one exists, matched best-effort on the visible label (the response gives a name, PrestaShop needs a shop-local id, and no match writes nothing rather than guessing), and otherwise is appended to `city` as `"Ashford, Kent"` rather than dropped
  - **`address2` and the state field join the pinned set.** They are added to `MIRRORED_ADDRESS_FIELDS` and `Twopayment::MIRROR_WRITE_SESSION_KEYS`, so the address-wide pin now judges them: a buyer typing a second address line or a county freezes the secondary address exactly as a buyer typing a city does. That is the point of the rule — a tracked set missing two writable fields would have made the pin miss real buyer-entered data. It does mean a buyer-typed second line now freezes an address where it previously did not, which is intended rather than incidental
  - **A `TWO:`-prefixed identifier is stored, paired, mirrored, routed and submitted exactly like any other organisation number — with one exception, forced by the platform: it is never written into the visible `dni` address field.** PrestaShop rejects it there outright (`Address` declares `'dni' => ['validate' => 'isDniLite', 'size' => 16]`, and `isDniLite` is `/^[0-9A-Za-z-.]{1,16}$/U` — a colon is not in the class and the value is 18 characters), so writing it made core refuse to save the address at all. It is also pointless — the plugin's own reader validates `dni` against `/^[A-Z0-9\-]{5,20}$/i` and so could never read it back — and semantically wrong: `Country::isNeedDniByCountryId()` is country-level, so `dni` is required of *every* buyer there. It is the buyer's own fiscal number (NIF/CIF), not a slot for ours. Leaving it alone blocks nobody: the buyer fills it as they always must
  - **The prefix is never stripped anywhere.** It is an integral part of the identifier and meaningless to the API without it, so it round-trips byte-identical everywhere it *is* stored — the hidden `companyid` input, the cart-scoped session record, the order-scoped record below, and the API payload
  - **There is no CSS/display rule on the identification field, deliberately.** An earlier round hid that field when it held an internal identifier; with the value no longer reaching it there is nothing to hide, and the hiding could never have been complete anyway — PrestaShop renders `dni` into address blocks, invoice PDFs and order emails via `AddressFormat::generateAddress()`, which no stylesheet reaches. The three genuine display surfaces (the hint under the company field, the search result rows, the order-intent sentence) continue to suppress it through the shared display predicate
  - **The address-wide pin is deliberately not consulted by the enrolment write**, and that too is a reversal of a review fix. The pin's scope resolves only when the invoice form is the *visible, editable* form — so gating on it gated the form the buyer was looking at and had just acted on; and an invoice form core pre-filled from a saved address is pinned by default (non-empty fields, nothing on record), which made the adoption write nothing at all for every buyer editing an existing billing address. The mirror's pin is right for the mirror, which carries values across a page load into a form the buyer never asked it to touch; it is wrong for an enrolment the buyer has just completed in front of them
  - **A blank `company_name` writes no identity at all** — no company name, no hidden `companyid`, no `dni` — because the name is the only value the pairing tag can carry without making the confirmed-selection check lie. The address still fills. It does now **disown a selection that was standing before the buyer enrolled** (hidden pair, tag, hint, lookup-written `dni`), which otherwise left the form naming an abandoned company while the session said sole trader. Cleared field by field and deliberately *not* through `clearSelectedCompany()`, which would also clear the server session company this enrolment had just written. Residual needing a ruling: the visible company field keeps whatever it held
- **Clicking "I'm a sole trader" on the address-editor page dead-ended in silence** (TWO-40 follow-up, live bug on staging)
  - Root cause: the token-mint endpoint refused any cart with no `id_address_invoice`, which on the address editor is *most* carts - the buyer is editing the very address the check demanded. The browser then had nowhere to render the refusal (the error element lives in the payment tile's `.two-sole-trader` container, which never exists on that page), so the entry point looked simply dead
  - The invoice-address precondition is replaced by a country resolver: the posted `country`, accepted only in exactly the two-upper-case-letter ISO shape, and the cart's delivery address as a last resort for a request that carried no usable country at all. Nothing resolvable is still a refusal - now worded as a country problem rather than an address one. (This resolver initially put the cart's invoice address ahead of the posted value; see "the sole-trader country now comes from the buyer's live selection" below for why that was inverted and the invoice tier deleted)
  - **The authorisation gate is unchanged**: minting still requires the registry to say the flow is available for a resolved country, re-evaluated server-side on every call. Accepting a posted country grants no privilege - the mint takes no country at all (the tokens are country-independent), the registry check still runs on the server, and the availability endpoint already answers any client-supplied country by design. So the posted value can only move the answer from "unresolved" to "the registry's own answer for a real country"
  - The country the browser posts is the same resolver the "Sole Trader" chip's own visibility is decided from, so the mint gate and the chip cannot disagree about which country the buyer is in

- **Sole-trader delegated-auth tokens are minted when the checkout page resolves an eligible billing country, not on the buyer's first "I'm a sole trader" click** (TWO-40). The 30-minute background refresh is armed at that same point, so by the time the buyer clicks, a token pair is already minted and being kept alive and the click has only the autofill lookup between it and the signup popup — one fewer round trip inside the gesture that has to open a popup window
  - **Gated on the availability answer that already decides whether the chip is offered at all**, so a buyer whose billing country does not support sole traders costs no mint. One attempt per country rather than one per availability resolution: a failed mint is not re-issued every time the answer resolves again, and a country change *does* re-mint, because the country the tokens are authorised against must not drift from the country the chip is being shown for
  - **Only a mint a click is actually waiting on is ever acted on.** Whether minted tokens open a popup or start a buyer lookup no longer keys off whether an enrolment is nominally in progress, which is the wrong test in three separate states: the eager mint has nobody waiting on it, an enrolment stays nominally in progress after a failed click (so a later country change would resume it), and a click abandoned while its mint was in flight has already been settled by the abandonment.   - **A failed eager mint stays silent**: no error appears in the enrolment container, and the retry cooldown is not started, so the buyer's first click is free to mint immediately rather than opening onto an error it did not cause

- **The company-search location setting is renamed `PS_TWO_ENABLE_COMPANY_NAME` -> `PS_ENABLE_COMPANY_SEARCH_IN_ADDRESS`, migrated by `upgrade/upgrade-2.7.6.php`** (TWO-40 item #1, version 2.7.6)
  - The old name said "enable company name", which stopped being what the switch does at TWO-25326 §7.1: it decides WHERE the one company-search control renders (address entry vs payment tile), never whether it exists.   - **The migration is deliberately GLOBAL-TIER-ONLY, and that is a real accepted tradeoff.** PrestaShop has three configuration tiers (global / shop-group / shop). `Configuration::get()` resolves across them against the ambient context and `Configuration::updateValue()` writes into whichever tier that context selects, but `Configuration::deleteByName()` is name-wide and unconditional with no per-tier variant. So the script carries exactly one value — the one the upgrade's own context resolved, in practice the global row — and then deletes every row of the old key at every tier. A shop-group or per-shop OVERRIDE of the old key is destroyed without being carried, and that shop reverts to the default (address area) instead of the position its merchant chose
  - Accepted on Doug's explicit ruling: this module has no live merchants, so no such override exists in the wild. The tier-exact alternative was attempted three times on the withdrawn attempt and produced three distinct variants of silent merchant data loss, each fix correct about its own defect and introducing a new one, because every one of them tried to infer a row's tier from an API that resolves across tiers. `.ai/decisions.md` keeps the record of what a safe rename requires — direct row-by-row `ps_configuration` SQL, multistore CI coverage, and a shop dimension in the offline `Configuration` test double. **If this plugin ever has multistore merchants, that is the work; the 2.7.6 script does not cover it**
  - **File-swap caveat, which the script cannot close.** Upgrade scripts only run via the back-office **Module Manager → Upgrade** action or `dev/ci/upgrade-module.sh`. A deploy that merely replaces the module's files — which is how the git-synced shops update — does NOT run them, and neither does opening the module's own *configuration* page: no PrestaShop code path executes `upgrade/*.php` from there. Between the file swap and the upgrade actually being run the new key is absent, the resolver falls back to its default, and a shop configured for tile mode silently gets the search back in the address area on a live storefront
  - Address autofill comes back with it **only where `PS_TWO_ADDRESS_LOOKUP` is absent or `1`**. `getAddressLookupEnabled()` force-returns `'0'` while the search is not in the address area, so once the resolver flips back to the address-area default it reads that row again — but a shop that picked tile mode *through the admin form* had that row written to `0` by the same save (the write is gated on `isAddressLookupSettingAvailable()`), so autofill stays off there. The autofill half of the window therefore bites shops whose tile mode was seeded programmatically, as the e2e tile-location spec does, not ones that clicked it in the back office
  - There is deliberately **no** read shim for the old key (Doug: "not a permanent alias"), so running the upgrade once after a file-swap deploy — Module Manager → Upgrade, or `dev/ci/upgrade-module.sh` — is a real release step
  - **If the copy cannot be written, the old row is kept rather than deleted, and the upgrade still succeeds.** `Configuration::updateValue()` can answer falsy or raise, and in either case the old row is then the only surviving copy of the merchant's position, so removing it would destroy the value the script exists to preserve. That path logs at severity 3 and names the recovery: **a human re-selecting the position on the module's configuration page, or copying the value across in `ps_configuration`**. There is no automatic retry, and the log does not offer one — the script returns `true`, so the module is recorded at 2.7.6 and version-gated discovery never runs it again. Returning `false` to make it re-runnable was rejected: core `disable()`s a module whose upgrade script returns falsy, which removes the payment method from the storefront and strips the module's `override/` files out of the shop, and that is a far worse outcome than one setting landing on its default
  - **The copy is guarded on the new key too**, not only on the old one: the window above lets a merchant save a position before the upgrade has ever run (new key written, old row still holding the previous position), and an unguarded copy would later overwrite that choice and move the search back to the address area. `upgrade/upgrade-2.7.6.php` copies only when the new key holds no usable value, treating `''` as absent exactly as the resolver does — deliberately not `Configuration::hasKey()`, which counts an empty row as set. Covered offline by `tests/CompanySearchLocationKeyMigrationSpec.php` and against real core by the `upgrade-smoke` job
- **The sole-trader country now comes from the buyer's live selection, and the cart's committed invoice address is no longer consulted at all** (TWO-40, Doug's explicit ruling)
  - `resolveSoleTraderCountryIso()` used to read the cart's invoice address first and only then what the request posted. That is the wrong way round: the committed value is a snapshot the buyer may be in the middle of changing, so a buyer switching country in the address form was gated against the country they had just moved off
  - The posted country now wins outright, and the invoice-address tier is **deleted rather than demoted** — a lower tier would still silently win whenever a POST arrives without a country for an innocuous reason (an older cached script, a stripped body), which is the same bug in different clothes. The cart's delivery address is the sole last resort for that case
  - **The authorisation gate is unchanged and its regression cover is now doubled.** Minting still requires the registry to say the flow is available for the resolved country, server-side, on every call. Promoting the posted tier grants no privilege: the mint takes no country at all, the registry check still runs on the server, and the availability endpoint already answers any client-supplied country by design
  - The two-upper-case-letter shape check is untouched. It is what stops junk reaching the registry, and it was never the thing doing security work
- **A company chosen while entering the shipping address is now carried over to the invoice address, when the buyer has said the two addresses differ** (TWO-40, new behaviour — no equivalent on any other Two plugin yet)
  - Company **name**, its **organisation number** and the **country**. Street, postcode and city are deliberately excluded: the buyer has just stated this is a different address, and writing the company's registered street over it would overrule that statement
  - **The name and the number travel together, or neither travels.** Once the address is saved, the order-payload resolver can reach the tier that reads the company off the address itself, so a carried-over name with no organisation number beside it would mean an order carrying a company the buyer never typed and no number at all. A form whose identification field already holds the buyer's own number therefore gets neither write; a form with no identification field at all still gets the name, since the field's presence is decided by the country's address format and there is nowhere to put a number
  - **A country change cannot separate the two halves.** Whether the form carries an identification field is decided by the country — core appends it only for a country flagged as needing one, which on stock data is Spain and Mexico alone — so the carry-over's own country write can hand back a form whose fields are different from the ones it wrote into. Mirroring into such a country from one without the field used to leave the name beside an empty, *required* identification field that nothing was then allowed to fill; the reverse direction lost a number already written, because the rebuild's restore step cannot restore a field the new render does not emit. The two halves are therefore tracked separately — a number placed in a field versus one still owed — and the owed one is placed as soon as a field for it appears. That completion is gated on the carried-over **name** still being present and still marked as ours, never on the number field merely being empty, so no completion refills a number the buyer cleared themselves on a form that kept its identification field. That qualification is not the whole story, though: because the carry-over publishes the selection the way a real one does, the submit handler reads the published selection back and writes it into the identification field on the way out — same country, no rebuild, on the very next submit. A cleared number therefore returns by either of two routes, and the second one is deliberately left as it is, because it is exactly what a real selection does on that same form and the alternative is an order carrying a company name with no organisation number beside it. A further residual is accepted rather than closed: because a number is re-owed whenever the rebuild renders a country whose format has no identification field at all — decided by the field being absent, not by the value it held — a cleared number does come back if the buyer leaves for such a country and returns. The field is only ever absent on countries that do not require a number and only ever completed on countries that do, and the shop rejects an empty required identification number at save, so the cleared state being lost is one that could not have been submitted
  - It is a **cross-page-load** operation, because PrestaShop leaves no alternative: core never renders two editable address forms at once (the delivery and invoice form flags are set in mutually exclusive branches), so at the moment a company is picked there are no invoice inputs on the page to write into — the invoice side is a radio selector over saved addresses, or absent. The buyer reveals the invoice form by following a link whose href navigates, so there is no client-side reveal to listen for either. The carry-over therefore runs when the company-search control mounts on the invoice form
  - **A true no-op unless every one of these holds**: the merchant's "Autofill company address" switch is on (so this is inert on the payment-tile mount, where that switch is forced off), the editable form on screen is the invoice one, the buyer's current state says the two addresses differ, and a company selection exists for the current cart. When the buyer has not said the addresses differ there is one address and nothing is populated
  - **A value the buyer typed is never overwritten.** Every field lookup is scoped to the visible form element rather than the document. For the country select, "unanswered" means **still exactly the country the shop rendered** rather than empty — an address form's country select is never empty, so an emptiness test would have made the country half of this dead code. The rule that decides whether a field may be written is the address-wide pin below, not this bullet alone
  - **A field the buyer deliberately cleared stays cleared.** Populating happens at most once per company per page. That matters because a country change makes PrestaShop rebuild the address form around the buyer and restore the previous field values, so a "fill it if it is empty" rule would silently undo the clear. The same rebuild drops the autofill marker (core restores values, not attributes), so a separate step re-establishes the marker on values still recognisable as ours — re-marking is never allowed to write a value
  - Requires the stored company selection to be readable by the browser, so the module now publishes the cart-scoped record into the checkout JS config. That publish applies the same checks the order payload applies — the company/number pair, the country agreement, the captured address — but is **read-only**: it runs on every checkout render, and a record it declines to publish is left intact for the consuming path to judge rather than destroyed
- **Syncing into the invoice address stops as soon as the buyer has entered anything there, and it stops for the WHOLE address** (TWO-40, Doug's explicit ruling — this replaces the per-field "write it if it is unanswered" rule described above)
  - Six fields are compared: company, organisation number, country, street, postcode and city. If **any one** of them no longer holds what the plugin last wrote there, the entire invoice address is treated as the buyer's own and **nothing** is synced into it. So the sync only ever writes into a pristine invoice address, and once the buyer touches a single field it stays frozen for the rest of the cart
  - The comparison is against **what the plugin last wrote**, never against the primary address's current value. Comparing against the current value cannot work: the instant the primary changes, the invoice address no longer matches it, so every legitimate re-sync would read as a buyer edit and syncing would stop for good
  - Values are compared **trimmed and case-insensitively**, so surrounding space or a difference of case only is not the buyer authoring a different answer. The country is compared as a resolved ISO code, never as an option value or its visible label
  - **There is no "these addresses are the same" control and none was added.** Syncing resumes on its own: once the contents match what the plugin last wrote again, the address is no longer pinned. That also means an invoice address the buyer opens to **edit an existing saved address** is pinned immediately — its fields hold the buyer's own data with nothing on record as written there — so a saved address is never silently rewritten
  - The autofill marker cannot carry this on its own, because a country change makes PrestaShop rebuild the address form and its restore copies values but not attributes, while the pin is evaluated on the page load *after* that. So the plugin also records what it wrote in a **cart-scoped record of its own**, published to the browser. It is deliberately separate from the cart-scoped company record, whose contract is to be destroyed by the country and address guards — this has to outlive all of that
  - The company autofill's street/postcode/city writes are now scoped to the address block they are meant for. Where the invoice form is on screen but no block can be identified, the fill is **skipped** rather than falling back to a document-wide write: an unattributed write would be read as the buyer's own on the next render and would pin the address permanently
- **The buyer's stored company selection is now scoped to the cart it was chosen in** (TWO-40, Doug's explicit ruling)
  - The selection is only needed up to the point of order placement and nothing further. It is now stamped with the cart id it was chosen under (`two_company_cart_id`), and a stored record whose cart id does not match the current cart is treated as **absent** and cleared. An ordered cart is never carried again — once an order references it, the next request's `FrontController::init()` finds `Cart::orderExists()` true, unsets the cookie's `id_cart` and assigns a brand-new cart — so a company picked for one order can no longer be read back on a later one. That rotation lands on the *following* request rather than inside placement, so the record stays readable for the rest of the request that places the order
  - **This is a real behaviour change.** The record used to survive for an hour regardless of which cart or order the buyer moved on to. It is also unreadable after placement, which is intended rather than a side effect
  - **The cookie's expiry is deliberately unchanged, because of the cookie's shape rather than any other key depending on the hour.** `Cookie::setExpire()` assigns one expiry scalar for the whole cookie — the value handed to `setcookie()` — so there is no per-key expiry to set and any call would silently re-time every other key sharing the cookie. Dropping the writes' `setExpire` is not neutral either: the lifetime falls back to whatever `config.inc.php` computes from `PS_COOKIE_LIFETIME_FO`, which is shop configuration — a positive value gives that many hours, `0` gives a cookie that dies with the browser session — so it can be longer *or* shorter than an hour. Cart scoping, not the expiry, is what bounds the record's usable life
  - The five keys are centralised behind a writer/reader/clearer trio on `Twopayment`, so a write site cannot add a field without the cart stamp and a clear site cannot miss one. **A record written by an earlier version carries no stamp, so it reads as absent and is cleared** — there is no migration, by design: the whole cost is that the buyer re-picks their company
  - Both existing invalidation guards are unchanged and now have their own regression cover: the country-mismatch wipe and the wipe of a record carrying no country marker. Cart scoping is an extra axis, not a replacement — a buyer can change address country inside one cart
  - **A request with no loaded cart stores nothing and clears nothing.** A record that could only be stamped `0` could never be read back, and the next read that did have a cart would clear it — destroying whatever selection was already there. The path that reaches this is the address-save hook firing on the My-Account address page, before the buyer has a cart
  - **A record carrying a company NAME but no organisation number now keeps its country marker across an address save.** Routing the address-save disown guard through the reader (`$previousRecord['id'] !== ''`, not `isset($cookie->two_company_id)`) means it no longer fires on a record with nothing to disown — an empty number is not a number that can be disowned. Order placement is still blocked in that state exactly as before; only which "pick a company" prompt the buyer sees next changes, not whether they are stopped. Pinned by `SessionCompanyClearSpec::testAddressSaveKeepsCountryMarkerWhenNumberWasAlreadyEmpty()`

- **The Two payment tile is now withheld from buyers outside the merchant's own per-module country allowlist, instead of failing at the last click** (TWO-25387)
  - PrestaShop has a native per-payment-module country allowlist, edited from the back office's Payment Restrictions screen and stored one row per (module, shop, country). It is a separate list from the shop's active countries, and a merchant who narrows it expects Two to simply not be on offer elsewhere
  - **Core disagrees with itself, and that is the bug.** At final order submission the payment controller asks core whether this module is authorised, and core's answer matches the allowlist against the cart's **invoice address** country. Core's *display-time* filter matches the same table against the **contextual** country — which the front controller resolves from whichever address `PS_TAX_ADDRESS_TYPE` names, and that defaults to the **delivery** address (checked on a stock PrestaShop 8 install rather than assumed). So on any cart whose delivery and invoice countries differ, core rendered the tile against one country, took the buyer through the whole payment step, and refused the order against the other at the last click
  - One further case lands here for the same reason: a merchant who switches that setting to the invoice address still gets no protection when the contextual `Country` fails to load at all, because core skips its country clause entirely in that state and dispatches to every payment module
  - **Scope, stated precisely: this narrows what core offered, it cannot widen it.** Core's opposite failure — refusing to dispatch `paymentOptions` at all when the *contextual* country is not allowlisted even though the invoice country is, so the submission would have succeeded — happens before this module is consulted and is untouched here. That direction remains core's behaviour
  - `hookPaymentOptions()` now consults a new `checkCountry()` alongside `checkCurrency()`, and withholds the payment option with a log line when the billing country is not enabled — the same shape, and the same reasoning, as the unsupported-currency gate that already sat next to it. Logged once per request, not once per evaluation: a narrow allowlist is a permanent setting, so unlike a transient outage *every* out-of-allowlist buyer would otherwise write several `ps_log` rows on every render
  - Matched on the **invoice** address and the current shop specifically, because that is the exact pair core matches at submission. A gate that disagreed with core would not remove the dead end, only relocate it. There is no core convenience method for this the way `Module::getCurrency()` exists for currencies, so the lookup is inlined the way core's own readers of that table are
  - **Fail-closed on a genuine "no such row", fail-OPEN on a lookup that could not be answered at all.** A row core cannot find here is a row it will not find at submission either. But a failed query is not a restriction verdict, and treating it as one hides Two on every shop at once — which is not hypothetical: the first cut of this gate carried a redundant `LIMIT 1` (core's `Db::getValue()` appends its own, so every lookup was a syntax error), and under a uniformly fail-closed branch that silently removed the payment method from every shop. Only the Playwright e2e job caught it
  - **Telling those two apart needs more than a `try`/`catch`.** On the module's declared floor (`ps_versions_compliancy` min 1.7.6.0) a failed query does not throw at all — `DbPDO::_query()` is a bare `link->query()`, and `DbMySQLi`'s is unwrapped too — so `Db::getValue()` returns `false` for a broken query and for an absent row alike. The gate therefore also consults `Db::getNumberError()` before believing a `false`. The `catch` alone would have been correct only on PS 8 with the PDO driver, where PHP 8's `ERRMODE_EXCEPTION` default happens to surface it
  - The offline harness now models both drivers: `Db::getValue()` rejects a query carrying its own `LIMIT` (reproducing the fatal), and can answer `false` with a driver errno *without* throwing, which is the floor-version behaviour no exception-based fixture can express. The emitted SQL is asserted directly, and the fail-open reason is logged once per request carrying the exception class or errno — never the driver message, which contains the SQL
  - A shop that has never touched the Payment Restrictions screen keeps every country that was **active when the module was installed** — that is what `PaymentModule::install()` writes, and core adds rows again when a country is created or toggled active from the country list. A country enabled by some other route gets no row and is withheld; that matches what core would do at submission, so it is not a regression, but it is not literally "unaffected" either

- **The `Registered business` / `Sole trader` chips stop flickering** (TWO-25326). Two independent causes, both in the sole-trader module and neither touched by the earlier tile-level mount/unmount fix. First, "already rendered" was recorded as a *country* rather than as a rendered container: PrestaShop replaces the payment fragment — and with it the whole toggle container — repeatedly while the checkout step settles, and the replacement arrives with no chips in it, so the module read the country as unchanged and returned early, leaving the chips missing from a container it believed it had already filled. Both causes above are real and stay fixed, but both are about not redoing work *after* the availability answer arrives — and the flicker lives entirely in the window *before* it arrives. Measured on the staging shop: the toggle is `display: none` with zero chips at first paint and only becomes visible with two chips ~280ms later, on **every** load, because the chips were built only in the browser and only after a round trip. Both layers already refuse to cache an error on their own; the handover now refuses to as well, and the client's retrying path stays live. It renders inside a shopper's checkout request, and a payment-option change reloads that page — so resolving live meant every payment-step render on a shop that cannot reach the registry paid the request timeout again, which is net-new buyer-visible latency on a path that previously made no call at all. The browser's own availability request resolves an unknown answer off the render path and the endpoint answering it writes the cookie, so ordinarily the *first* payment-step render of a session shows no toggle and every render after it — including all the surcharge-driven reloads that made the flicker visible — is served from cache. Where the cookie cannot be stored at all, or the registry keeps failing, every render answers "unknown" and the toggle is client-rendered exactly as it was before this ticket: degraded to the old behaviour, never worse than it. The registry lookup itself now also carries the tight checkout timeout rather than the 60-second default sized for file uploads
  - **An availability request already in flight can no longer overwrite an answer adopted while it was out** (round 3 review; this was the round's blocker). A load that starts with no server answer fetches one; PrestaShop then replaces the payment fragment with one that *does* carry an answer, which is adopted; the outstanding request then answers, having been issued before the server's answer existed. Worse than merely stale: the failure branch applied "not available" while the cached answer still said available, so the settled-check then agreed the toggle was correct and it stayed hidden for the rest of the page's life — the exact laundering this ticket removed, re-entering through the client. Adoption now bumps a generation counter that both request continuations check before they write anything
  - The toggle's country now comes from the **cart's billing address**, not the shop's own country (round 3 review).   - The sole-trader module gained a `destroy()` that detaches every page-level subscription. ### Fixed
- **A surcharge cap of 0 is refused at entry, and a stored 0 is no longer relayed as "no cap"** (TWO-25289, umbrella TWO-24739)
  - **The overcharge.** `TwoSurchargeCalculator::buildBuyerFeeShare()` tested the configured cap with `> 0`, so a cap of exactly `0` was normalised to **absent** — and absence is what means "uncapped". A merchant who configured `0` therefore got an **uncapped** percentage surcharge: the opposite of the instruction, and an overcharge to the buyer. It is now relayed as `cap => 0`, which bounds the fee at zero
  - **Absent and zero are now distinguishable at the settings boundary too.** `getTwoSurchargeSettings()` cast the cap unconditionally, and an unset `Configuration` key reads back as `false` with `(float) false === 0.0`, so "no cap configured" and "a cap of zero" were the same value before the calculator ever saw them. A blank cap now reads back as `null`; anything numeric, zero included, is a real configured cap. The save path already stores `''` for a blank cell, so blank is the honest unconfigured signal
  - **Refused on save.** `validTwoSurchargeFormValues()` now rejects any cap that rounds away at 2dp — `0`, `0.0`, `0.00`, `00` and sub-cent values like `0.001` alike, since the cap is rounded before it is sent and a sub-cent cap would otherwise arrive as a hard `0.00` one step later. `0.005` rounds *up* to `0.01` and survives. The error says what to do instead. A cap of `0` is never what a merchant means by it: the cap bounds the **whole fee** — the percentage and the fixed fee together, not the percentage alone — so it silently wipes a configured fixed fee too, and the intent it gets mistaken for is expressible directly with 0% and a 0 fixed fee. A **blank** cap stays valid and still means "no cap"
  - **No migration**, and therefore no new upgrade script: no configuration key is added, renamed or rewritten. An already-stored `0` is not migrated — it now relays as a genuine zero cap, i.e. no fee, which is the safe reading of it. **Consequence, stated plainly:** on a shop that already has a cap of `0` (or a sub-cent one) stored against a term, the Payment Settings tab cannot be saved while the cap column is visible until that cell is cleared or given a real value — the save aborts on any validation error. The cell is visible and the error names the term, so it is actionable, and the rule is skipped entirely while the column is hidden so a fixed-only or disabled shop is never blocked
  - **Monetary values are rounded to 2dp before the request.** The pricing API refuses a value finer than two decimal places rather than rounding it, so an over-precise configured `surcharge` or `cap` was rejected upstream and surfaced to the buyer as a generic error. The cross-currency path already rounded at `convertTwoAmountBetweenCurrencies()`; the same-currency path did not, and now does. Plain half-up rounding — sub-cent caps, away-from-zero rounding and zero-decimal currencies are all deliberately out of scope, since the one value where the rounding direction would have mattered is now refused outright
  - **Admin copy.** The grid's cap column heading said `Cap on percentage`, which describes it wrongly; it is now `Cap`, with a note under the grid stating what the cap actually bounds and that `0` is not allowed
  - **Validation covers every RENDERED term, not the stored ticked subset.** The grid posts a row per offerable term, and the ticked subset is rewritten earlier in the same save than the surcharge values are read — so a cap typed on a term ticked in the same submit was stored without ever being validated, then relayed. An unsubmitted cell is now skipped explicitly rather than being reported as a non-numeric value
  - **A zero cap never withholds the payment method.** `isTwoSurchargeQuotableForCart()` fails closed on a missing FX rate and loops every offered term, so relaying a zero cap instead of dropping it would have taken Two offline for every buyer on a shop whose only currency-bearing member was a zero cap — over a conversion with no work to do. Zero needs no rate: it is zero in every currency, and is now skipped in `convertTwoBuyerFeeShareCurrency()`. This is the TWO-25276 regression shape reached by a different route, and it is covered by its own test
  - **Non-numeric and negative stored caps are absent, not zero.** Both would have cast to a real cap (`0.0` and `-10.0` respectively) and either suppressed the fee on a previously-uncapped shop or been refused upstream
  - **The cap help text is hidden with the cap column.** The column-visibility JS was scoped to the grid table; it now covers the whole form-group, so cap-only copy is not left on screen for a fixed-only surcharge
  - `translations/es.php` gains the four new/changed strings. That file carries no other surcharge-grid entry — a gap that predates this change and is untouched by it
- **Reverted: the zero-cap "overcharge" guard withheld Two from every buyer on affected shops** (TWO-25276, reverting part of TWO-25269, umbrella TWO-24739)
  - **The premise of the guard was false.** TWO-25269 (entry below) added a check in `convertTwoBuyerFeeShareCurrency()` that failed closed when a **configured** cap converted to `0.00`, on the stated reasoning that "a zero cap is indistinguishable downstream from *no* cap, so passing it through sends an uncapped percentage - an overcharge". The API does not behave that way: it tests the relayed cap for **presence**, not truthiness, an absent cap is what means "no cap", and its own test suite pins the zero-cap outcome. A zero cap therefore **bounds the fee at zero** (source references are recorded on TWO-25269 rather than quoted here - this repository is public and that service's is not): the surcharge is simply not applied, which is exactly what capping at zero asks for. There was never an overcharge to guard against
  - **The guard had a real, immediate cost.** `isTwoSurchargeQuotableForCart()` loops **every** offered term, and any single term whose configured cap rounded to `0.00` returned false, so `hookPaymentOptions()` returned `[]` and the Two payment method was withheld from **every buyer on the shop**. A behaviour regression on `staging`
  - **Reverted**: the `cap`-specific rounds-to-zero branch and its error log are gone; a converted cap of `0.00` now passes straight through as `cap => 0`. The quotability gate trips on the **no-FX-rate condition only**, which is term-independent and remains the correct fail-closed case
  - **Deliberately kept from TWO-25269**: the `isTwoSurchargeQuotableForCart()` gate itself and the `hookPaymentOptions()` early return for the no-rate case; the error-level no-rate log naming the currency pair and term (the fail-closed path previously threw with nothing logged at all); the fixed-`surcharge`-rounds-to-`0.00` case proceeding at `0.00` with an info log; the absent-cap skip (an absent cap still sends an uncapped percentage, by design); and the `applyTwoSurchargeCartLineSync()` fix that distinguishes an unavailable quote from a deselection
  - **No rounding was changed.** The pricing API rejects a monetary value finer than two decimal places rather than rounding it, so an unrounded figure is a validation error, not a more precise cap. Every `round($converted, 2)` stays
  - **No migration.** No configuration key and no database column, so no upgrade script and no version bump

- **A buyer surcharge that could not be priced in the cart currency was silently not charged at all** (TWO-25269, umbrella TWO-24739)
  - **This was believed to be safe and was not.** The previous reasoning was that PrestaShop was "already fail-closed because the quote is omitted". Both halves of that were wrong. `hookPaymentOptions()` never consulted the surcharge, the fee quote or FX at all - between the minimum-order gate and the return there was nothing but an unconditional "payment option shown" log. And `applyTwoSurchargeCartLineSync()` treated "quote unavailable" as equivalent to "surcharge deselected", removing the hidden surcharge cart line and returning **success**
  - **End-to-end consequence:** on a store whose cart currency had no FX rate against the currency the surcharge is configured in, Two was offered normally, the hidden surcharge line was deleted, and the order was created with a **zero surcharge and nothing logged**. Silent undercharge, on every affected order, with no signal that anything had happened
  - **Fix**: a new `isTwoSurchargeQuotableForCart()` gate withholds the payment option, reusing the existing mechanism - `hookPaymentOptions()` returns `[]`, exactly as the minimum-order gate already does. The checkout is never errored; Two simply is not offered. `applyTwoSurchargeCartLineSync()` now distinguishes an unavailable quote from a deselection: it leaves the cart line in place, reports failure and logs, instead of removing the line and claiming success
  - **The gate condition is deliberately term-independent.** No term is selected when payment options render, so the gate cannot ask whether the *chosen* term is quotable - and it does not need to, because the rate lookup for the (configured currency → cart currency) pair fails identically for every term. Gating on "any offered term is unquotable" would have taken a whole store offline over one misconfigured term. The condition is: surcharge enabled **and** cart currency differs from the surcharge's configured currency **and** at least one offered term carries a fixed or cap component **and** the rate is unresolvable. A percentage-only grid is currency-agnostic and never trips it
  - **Three rounds-to-zero cases, and PrestaShop previously detected none of them.** No rate resolvable → **fail closed**, error log. A **configured** cap whose converted value rounds to `0.00` → **fail closed**, error log. ⚠ **This second guard was reverted immediately afterwards under TWO-25276 - see the entry above. Its premise was false and it caused a live outage.** A **fixed** amount whose converted value rounds to `0.00` → **not a failure**: it is a legitimately tiny configured amount, genuinely negligible in a stronger currency, and `0.00` is the arithmetically correct answer. It proceeds, logged at info
  - **An absent cap is not a failure and never was.** "No cap defined" is a legitimate configuration meaning an uncapped percentage surcharge, and it continues to be charged normally with Two still offered
  - **Signals, where there were none.** `convertTwoAmountBetweenCurrencies()`, `convertTwoBuyerFeeShareCurrency()` and `fetchTwoTermFee()` logged nothing whatsoever, which is why this went unnoticed. Every fail-closed path now logs at error level naming the currency pair and the term; the negligible-fixed-amount case logs at info. The generic converter stays deliberately silent because it is shared with fail-soft display callers - the decision sites log instead
  - **The per-term chip previews stay fail-soft, deliberately.** `getTwoOfferedTermSurchargeAmounts()` is display, not charge: it shows a number, it never decides one, so a failed preview degrades that one chip rather than removing the payment option. This matches the Magento plugin, whose preview paths also degrade while only the authoritative total path fails closed
  - **No migration.** The change adds no configuration key and no database column, so there is no new upgrade script

- **A shop kept running the old copy of a changed override, forever and silently** (TWO-25265, umbrella TWO-24739)
  - A module's `override/` directory is a **template**, not deployed content. PrestaShop copies it into the **shop's** own override tree once, at install or reset, and from then on the shop's copy is the file that executes. Nothing rewrites that copy - not an upgrade, not a deploy that replaces the module directory, not a git-sync. `Module::addOverride()` cannot do it even when it runs: for every method the shop's copy already declares it **throws** rather than replacing, and it has no path that removes one
  - **Consequence, and it applies to every existing shop:** 2.7.0 changed `override/classes/form/CustomerAddressFormatter.php` to stop injecting the department and project fields into the billing address block (they moved into the payment tile). The module's copy changed correctly and shipped correctly. Every already-installed shop went on running the old one. Observed on a live staging shop: module version reported `2.7.0`, files on disk `2.7.0`, deploy green, and a `2.4.0`-stamped override still injecting both retired fields into the address form. The same shop lineage backs the shop that tracks the release branch, so the identical symptom was queued up for the 2.7.0 release
  - **Fix**: `upgrade-2.7.1.php` calls the new `TwoOverrideMigrator::refresh()`, which deletes the shop-level copy of each of the module's overrides when it is stale, rebuilds the class index, and re-runs `installOverrides()` so the current version's copy is written fresh. A **retired** override is simply never re-written, so retirement and change are the same code path rather than two
  - **It refuses to delete three kinds of file, deliberately.** A file carrying any **other** module's `module:` stamp - PrestaShop's `override/` tree is a *shared* merge target and several modules splice methods into one file, so deleting a co-owned file would silently uninstall someone else's override, a worse failure than the one being fixed. A file carrying **no** stamp, which is core's own or a merchant's hand-edit. And a file whose every stamp already reads the installed version, which is what makes a second run a genuine no-op. Co-owned and unreadable files are logged for a human, never touched
  - **It cannot fail an upgrade.** Every filesystem operation is guarded and the upgrade function returns true unconditionally: a shop that cannot be tidied must still finish upgrading
  - **Why a new version rather than an edit to `upgrade-2.7.0.php`**: PrestaShop discovers upgrade scripts **by filename** and runs them only for versions strictly above the installed one. The shop with the bug is already **on** 2.7.0, so anything appended to that script would never run there - `number_upgraded=0`, silently
  - **New CI gate so the convention cannot decay**: `.github/scripts/check-override-migration.sh` fails a pull request that changes or retires a file under `override/` without an upgrade script that migrates it, and is itself tested by `.github/scripts/test-check-override-migration.sh`. What it cannot see is written down in its header - most importantly, it reads the repository and never a shop, so it stops new instances of this defect and does not discover existing ones
  - **Not fixed here, because nothing in this repo can:** `.tpl` changes go stale on a shop for a different reason (a compiled Smarty template is never regenerated while `PS_SMARTY_FORCE_COMPILE` is `0`). That is shop configuration, handled chart-side

- **Company search gave up exactly when the server would have answered, and reported every failure as "no companies found"** (TWO-25231, umbrella TWO-24739)
  - **Client timeout raised from 10s to 30s.** The server's own retry envelope is `stop_after_delay(10)`, so a 10-second client timeout aborted the request at the precise moment a successful response would have arrived. The buyer was shown a failure for a search that had in fact just succeeded. The client's ceiling has to sit clear of the server's, not on top of it
  - **A failed search no longer renders as an empty dropdown.** The `error:` handler called `responseCallback([])`, which made a timeout, a 5xx, a network error and a genuinely empty result set completely indistinguishable at the UI. An empty dropdown reads to a buyer as "my company is not registered" - a reason to abandon checkout rather than to retry - so all four rendered as the worst possible interpretation. Real failures now show an explicit "search is temporarily unavailable, please try again" row. A **genuine abort stays silent**, because that is routine operation (the buyer typed another character, or the address form was re-rendered) and the replacement request drives the UI
  - **Failures are never cached.** A cached failure would keep showing the buyer an error after the service had recovered
  - **New `degraded: true` response flag is honoured.** The company-search endpoint can answer HTTP 200 with an empty or partial body when its upstream registry provider timed out, and flags that case. Read as `=== true` so an **absent** field is false: every response predating the flag lacks it, and the server side may not be deployed yet. Degraded *with* results still renders the results - partial data beats an error message - and only degraded with nothing to show produces the unavailable row
  - **In-field spinner restored on the code path that actually runs.** `renderLoading()` existed but only on the custom fallback path, and the spinner CSS was commented out, so on the live jQuery-UI path a slow-but-alive search was visually identical to a dead one. The rule is scoped to the company field itself rather than to every autocomplete in `.js-address-form`, and sets `background-image` rather than the `background` shorthand so it no longer forces a white background over the merchant's theme
  - **The 5-minute result cache now survives widget teardown.** It lived inside the `setupAutocomplete` closure, and `TwoCheckoutManager.handleAddressFormUpdate()` destroys and re-creates the widget on every `prestashop.on('updatedAddressForm')` - which PrestaShop fires for ordinary interactions such as changing country. Every one of those re-renders therefore restored a cold cache and the buyer re-paid a full API round trip for a term searched moments earlier. Moved to module scope, with TTL pruning and a 50-entry cap it did not previously need now that it outlives the widget. **Aborting the in-flight request on teardown is unchanged and still correct** - a response whose widget no longer exists has nowhere to render; only the cache is preserved
  - Debounce was already 300ms on both paths, matching the Magento and WooCommerce plugins; verified and left alone
  - **Re-setup of the company search is now idempotent**, which self-review found it was not. `setupAutocomplete()` is re-invoked from both the country-change listener and the `updatedAddressForm` handler with no intervening `destroy()`, and three things went wrong each time: the `updatedAddressForm` handler re-registered itself so the count **doubled on every event** (making the work per event grow exponentially, with none ever unregistered); the custom fallback path inserted another dropdown while leaving the previous one's input listener firing; and the field object cached by `init()` was reused even though PrestaShop **replaces** the address form's DOM on that event, so bindings landed on a detached input. Registration is now guarded, the fallback path tears the previous one down (unbinding its listeners, which removing the container never did), and the field is re-resolved before use
  - **A destroyed company-search instance can no longer act on the live field.** `TwoCheckoutManager.handleAddressFormUpdate()` destroys the instance and builds a fresh one on every `updatedAddressForm`, but the handler the instance registered on that same event **cannot be unregistered** - `prestashop.on` has no `off` - so a destroyed instance still gets called. That was harmless only for as long as it held a stale field object and its work landed on a detached node; once re-resolving the field against the live DOM was added above, the destroyed instance resolved to the **same live input** as its replacement and re-bound the widget with its own stale closures. Because its `organizationField` is still the detached hidden `companyid` input its own `init()` created, the selected company's organisation number was written somewhere that no longer submits - recoverable only when the address-lookup toggle is on and a live `dni` field exists to copy back from, and silently lost otherwise. `destroy()` now marks the instance and every event-reachable entry point stands down. The per-instance registration guard stops one instance registering repeatedly but not a new instance per event registering once each, so the handler count still grows by one per address-form update; they are inert after the check, which is what makes that acceptable
  - Teardown of the custom dropdown also clears its spinner class, is no longer skippable by an earlier failure in `destroy()`, and the destroyed check now covers every entry point reachable from an event - the country-change setup and its pending retry, the fallback path's input listener, and company selection itself. Selection through a destroyed instance would write the organisation number to a detached input, so it stands down rather than writing
  - `destroy()` unbinds the country listener from the element it actually bound. It re-queried only `select[name='id_country']`, while setup picks the first of five fallback selectors - so on a theme matching one of the others the listener was never removed, leaking a live handler per address-form update
  - The pending debounce timer is cleared on teardown. A tick surviving teardown called into the search, which bumped the sequence and aborted the **new** dropdown's in-flight request - that request then resolved as superseded, so its spinner was never cleared and the buyer was left on a permanent "Searching..." row
  - A widget left on a node the field moved off is released rather than abandoned, along with the `<ul class="ui-autocomplete">` menu jQuery UI appends to `document.body` rather than beside the input
  - jQuery UI is detected via `$.ui.autocomplete` rather than `$.fn.autocomplete` alone - the older bassistance plugin of the same name has an incompatible signature, and feeding it the options object left the field with no working search while also skipping the fallback
  - No `Configuration` key is added and no upgrade script is needed, so this carries no version bump of its own

  - The hidden fee product carries the selected group on its `id_tax_rules_group` like any real product, so PrestaShop's native tax engine applies per-country/state rules, combined multi-rate stacking, and destination-based zero-rating (no rule for the destination = untaxed) to the fee line
  - The tax rate reported to Two's order API is resolved through the same core machinery (`TaxManagerFactory`) for the cart's tax address, with the same shop-wide gates (taxes disabled, VAT-number B2B exemption), so the PrestaShop line and the Two payload cannot drift and the order-create parity gate holds on cross-border orders
  - Selecting "No tax" (PrestaShop's built-in id-0 group) keeps the fee untaxed for every destination; an unset/invalid selection fails safe to "No tax"
  - Removed: the module-managed synthetic Tax/TaxRulesGroup/TaxRule graph, its `PS_TWO_SURCHARGE_TAX_SETUP` tracking blob, self-heal/advisory-lock machinery and uninstall cleanup (never released; uninstall still deletes the legacy configuration rows).
